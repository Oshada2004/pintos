### ALGORITHMS

>A2: Briefly describe what happens in a call to timer_sleep(),
>including the effects of the timer interrupt handler.

In `timer_sleep()`:

1. Returns `ticks>0` immediately
2. Computes wakeup tick as `timer_ticks()+ticks`
3. disable interrupts to avoid race conditions with `timer_interrupt()`
4. Sets `wakeup_tick` of cuurent thread and inserts it into `sleep_list` which gets sorted respect to `wakeup_tick`
5. Invokes `thread_block()` to change thread state to `THREAD_BLOCKED` and triggers a context switch

In `timer_interrupt()`:

1. `ticks` is incremented.
2. Inspects `sleep_list` starting from the front
3. For each thread whose `wakeup_tick<=ticks`, it removes the thread from `sleep_list`, calls `thread_unblock()` and places it on `ready_list`
4. Because the list is kept sorted it gets the first thread whose `wakeup_tick>ticks`

>A3: What steps are taken to minimize the amount of time spent in
>the timer interrupt handler?

`sleep_list` is maintained in sorted order by `wakeup_tick` upon insert.
So `timer_interrupt()` only checks threads until it finds one whose wakeup tick has not yet arrived and then terminates the loop.
The cost of maintaining sorted order is shifted entirely out of the interrupt context and into the calling thread in `timer_sleep()`.

### SYNCHRONIZATION

>A4: How are race conditions avoided when multiple threads call
>timer_sleep() simultaneously?

Race conditions are avoided by disabling interrupts via `intr_disable()` before accessing or modifying `sleep_list`.
Since Pintos has a uniprocessor architecture, disabling interrupts guarantees that the running thread cannot be preempted by another kernel thread while updating thread fields/inserting into `sleep_list`.

>A5: How are race conditions avoided when a timer interrupt occurs
>during a call to timer_sleep()?

Before the thread adds itself to `sleep_list` and calls `thread_block()`, it disables interrupts using `intr_disable()`.
Therefore, `timer_interrupt()` can't modify `sleep_list` while an insertion is halfway completed.
Interrupts remain disabled during context switching and are enabled only after the thread resumes execution.

### RATIONALE

>A6: Why did you choose this design?  In what ways is it superior to
>another design you considered?

An alternative design was an unsorted list, where inserting into the list takes lesser time, but `timer_interrupt()` must traverse every element on every tick.

The chosen design uses an ordered list sorted by `wakeup_tick` upon insertion.
With a sorted list, `timer_interrupt()` only checks the front element.
The cost of `list_insert_ordered()` is borne by the thread which is outside of the interrupt context, without reducing performance in `timer_interrupt()` making it fast.

>B2: Explain the data structure used to track priority donation.
>Use ASCII art to diagram a nested donation. (Alternately, submit a
>.png file.)

Each thread contains an intrusive linked list named `donations`.
When a high priority thread blocks on a lock held by a low priority thread, the waiting thread registers itself in the holder's `donations` list via its `donation_elem`.
It also records the specific lock in `wait_on_lock`.
The holder's effective `priority` is then computed as the maximum between its own `base_priority` and the priorities of all threads residing in its `donations` list.

### ALGORITHMS

>B3: How do you ensure that the highest priority thread waiting for
>a lock, semaphore, or condition variable wakes up first?

1. **Semaphores/Locks**: In `sema_down()`, waiting threads are inserted into `sema->waiters` using `list_inser_ordered()` sorted descending by priority. Also in `sema_up()`, `list_sort()` is invoked prior to popping `sema->waiters` to reorder threads in case priorities shifted dynamically due to donations.
2. **Condition Variables**: Each thread waiting in `cond_wait()` pushes a `struct semaphore_elem` to `cond->waiters`. In `cond_signal()`, `cond->waiters` is sorted descending by priority, ensuring the semaphore containing the highest-priority thread is signaled first.
3. **Ready Queue**: Both `thread_unblock()` and `thread_yield()` use `list_insert_ordered()` to keep `ready_list` sorted by priority so that `next_thread_to_run()` always selects the highest priority thread.

>B4: Describe the sequence of events when a call to lock_acquire()
>causes a priority donation.  How is nested donation handled?

When a thread `cur` calls `lock_acquire(lock)`:

1. It verifies whether the lock is currently held(`lock->holder!=NULL`).
2. If held, `cur` sets its `wait_on_lock=lock` and inserts itself into `lock->holder->donations` via `donation_elem`.
3. `thread_donate_priority()` is invoked.
4. To handle nested donation, an iterative loop tracks dependencies up to a maximum depth of 8:
   * It inspects the current lock's holder.
   * If `(cur->priority)>(holder->priority)`, `holder->priority` is updated to `cur->priority`.
   * If the holder is currently runnable, it is removed from `ready_list` and inserted using `list_insert_ordered()` to maintain sorted run queue order.
   * It advances to the next level by setting the lock pointer to `holder->wait_on_lock` and repeats.
5. The thread then calls `sema_down(&lock->semaphore)` and blocks.
6. Upon waking, `cur->wait_on_lock=NULL`, `lock->holder=cur`, and execution proceeds.

>B5: Describe the sequence of events when lock_release() is called
>on a lock that a higher-priority thread is waiting for.

When a thread calls `lock_release(lock)`:

1. It invokes `thread_remove_lock_donation(lock)`, which traverses the releasing thread's `donations` list and removes every thread whose `wait_on_lock==lock`.
2. It calls `thread_update_priority(thread_current())` to calculate the releasing thread's effective priority:
   * If other locks are still held with donors, the priority becomes the maximum among `base_priority` and the remaining donors.
   * If no donations remain, its priority drops back to `base_priority`.
3. It sets `lock->holder=NULL`.
4. It calls `sema_up(&lock->semaphore)`, which unblocks the highest priority waiter from `sema->waiters` and places it on `ready_list`.
5. It triggers `thread_test_preemption()` to yield the CPU immediately if the newly awake waiter outranks the releasing thread's updated priority.

### SYNCHRONIZATION

>B6: Describe a potential race in thread_set_priority() and explain
>how your implementation avoids it.  Can you use a lock to avoid
>this race?

A thread lowering its own priority via `thread_set_priority()` while another thread on an interrupt or different context attempts to donate priority to it or modify synchronization queues could cause inconsistent effective priority states or missed preemptions. Modifying `base_priority` while traversing `donations` could leave the thread scheduled incorrectly relative to threads on `ready_list`.

In `thread_set_priority()`, preemption and priority updating are performed atomically relative to thread switching. Preemption checks disable interrupts (`intr_disable()`) when accessing `ready_list`, ensuring that the priority state evaluation and context switch(if `cur->priority` is no longer the highest) occur without race conditions.

A lock cannot be used to avoid this race. Locks in Pintos are built on top of semaphores and threads, which themselves rely on priority scheduling and `thread_set_priority()`. Using locks inside priority setting functions creates recursive dependency loops and deadlocks. And also locks cannot be acquired in interrupt contexts. Disabling interrupts via `intr_disable()` is required.

### RATIONALE

>B7: Why did you choose this design?  In what ways is it superior to
>another design you considered?

**Alternative design:**
Tracking donations directly within `struct lock` by storing `max_priority` per lock and having threads maintain a list of held locks.

**Current design:**

1. **Accurate Tracking of Multiple Donors:** Maintaining an explicit `donations` list on each thread allows exact reconstruction of effective priorities when multiple threads donate to the same thread across different locks. When a lock is released, only the donors tied to that specific lock are discarded, while donations from other held locks remain intact.
2. **Deterministic Nesting Resolution:** The explicit pointer `wait_on_lock` allows direct directed graph traversal from donor to root holder, avoiding speculative depth searches across all system locks.
